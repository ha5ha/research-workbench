# 实验科研工作台产品计划 v0.2

日期：2026-10-21。本文聚焦实验工作流，是可评审的产品方案，不代表功能已经实现。产品首批用户以使用代码、数据和计算资源开展研究的学生与个人研究者为主；流程概念保持通用，领域差异通过项目配置和适配器承接。

## 产品定位

产品本质上是一个通用桌面 Agent 执行底座，加上一层科研流程和记录能力。用户像使用 Codex 或 DeepSeek Harness 一样，在主要由对话构成的工作台里让 Agent 阅读文件、修改代码、运行命令、检查结果；科研层让这些动作有明确的问题归属、审批边界、运行身份、数据证据和后续决策。

对话是主要工作面；问题、实验任务书、运行、数据和事实是对话所处的持久研究上下文。Agent 可以在聊天中提出结构化对象，用户可以直接接受、编辑或拒绝。关键研究记录从聊天中提取并保存为独立对象，换窗口、换模型或会话很长时仍然可找回。

首版聚焦计算型实验的完整闭环：

> 建立课题 → 提供背景 → 确认问题 → 拆分子任务 → 审阅并批准实验任务书 → 执行与定时检查 → 归档和分析结果 → 形成证据与下一步建议

“课题”在这里相当于研究项目；“问题”限定要回答的研究问题；“子任务”组织问题下可交付的一段工作；“实验任务书”冻结一次实验的条件与验收要求；“运行”记录某次真实执行。它们不能相互替代：一个子任务可以含多份实验任务书，一份任务书可产生多个有界运行尝试，一条聊天消息也不等于正式研究记录。

## 用户和首版边界

首批用户需要在本机或服务器上运行代码、反复生成实验输出，并在多轮迭代后仍能解释“为什么做了这次实验、数据在哪里、结论依据什么、下一步为什么这么选”。首版优先支持计算机方向常见的脚本、表格、日志、配置和图表。产品不假设某个特定学科、模型、数据集、统计指标或服务器供应商。

首版需要证明：用户可以在同一个课题下开多个问题分支和聊天窗口；Agent 能提出可审阅的实验计划；经授权的任务可以可靠运行、恢复状态、整理输出并生成可追溯分析；下一步建议可以回到研究者手中决策。论文库、跨项目知识网络、复杂团队协作和全学科实验模板可后续扩展，不阻塞当前实验闭环。

## 桌面工作台与主要交互

界面采用低噪声、以对话为中心的布局，参考 Codex 和 DeepSeek Harness 的工作方式：用户看到一个熟悉的 Agent 工作区，再按需要展开代码、运行、数据和研究状态。科研结构帮助定位上下文，不应把主界面变成密集仪表盘。风格可借鉴导航与操作模式，但视觉资产和交互细节需形成自己的设计。

| 区域 | 首版内容 | 使用目的 |
| --- | --- | --- |
| 左侧导航 | 课题切换、当前课题的问题树、会话列表、待审批计数；其他研究模块可暂时不出现 | 快速切换研究分支与聊天，不把课题与会话混为一体 |
| 中央工作面 | 默认对话；顶部可切换代码/文件、任务计划、运行日志、数据结果等视图 | 保持对话为主要交互，同时能检查 Agent 实际操作与结果 |
| 右侧状态栏 | 当前问题和子任务、运行阶段、最近/下次检查、资源预算、关联证据及待决定项 | 随时看清 Agent 正在做什么、基于什么、卡在哪里 |
| 对话内研究卡片 | 问题/子任务提案、实验任务书、批准请求、运行结果、分析发现、下一步建议 | 在同一对话里完成讨论和明确的科研状态转换 |
| 底部或侧边抽屉 | 命令输出、长日志、运行队列、差异和明细数据 | 需要时查看细节，默认不挤占主对话 |

用户创建课题后，主界面直接进入对话。欢迎引导允许用户先添加背景文件或描述当前问题，也可以在对话中补充。Agent 回答时可将文本、引用、代码差异、运行状态和数据摘要作为不同类型的消息卡片展示。用户不需要为了查看代码离开当前问题；切换“代码”视图是检查正在编辑的文件或差异，不会把代码视图误认为另一个独立项目。

左侧问题树与聊天会话分离。一个问题可以有多个会话，例如方案讨论、执行跟进和结果复核；新建会话自动加载所选问题的当前有效状态，不复制另一窗口的全部对话。用户从任何会话都可打开同一份实验任务书或运行记录，避免会话内出现彼此矛盾的状态。

## 核心研究对象

对象要足够通用，能够连接不同课题；领域专属字段应由模板或适配器提供。核心对象建议如下。

| 对象 | 定义 | 核心字段或关系 |
| --- | --- | --- |
| 课题 | 独立研究空间，类似项目 | 名称、研究目标、背景材料、策略与权限、资源位置、成员、当前焦点 |
| 背景材料 | 人工提供或导入的上下文 | 文件/URL/文本来源、作者或添加人、时间、版本、可用范围、备注；人工陈述默认标作待核验背景 |
| 问题 | 有边界、可持续追踪的研究目标 | 要回答的内容、动机、完成条件、父问题/关联问题、状态、负责人、来源和审核记录 |
| 子任务 | 问题下一个有界工作单元 | 目标、交付物、依赖、完成条件、责任人、状态；可关联多次实验或人工工作 |
| 实验任务书 | 一次已版本化的实验设计和执行合同 | 目的、假设/预测、比较条件、输入、方法/代码版本、预算、执行位置、产物清单、分析与验收计划、停止条件 |
| 运行尝试 | 任务书的一次实际派发与执行 | 唯一 run ID、任务书版本、代码/输入/配置身份、环境、命令、启动凭证、状态事件、日志、产物和成本 |
| 产物/证据 | 原始文件或派生结果的规范身份 | 来源运行或外部来源、内容哈希、位置、格式、模式、版本、敏感性、父产物和用途 |
| 分析记录 | 对特定运行或数据版本的一次可复算分析 | 脚本/分析器版本、参数、比较范围、结果表图、质量检查、解释、限制和引用 |
| 事实/发现 | 对证据的结构化表达 | 观察、指标、解释、文献主张或审核结论等类型；状态、适用范围、支持/反证、依据和更正链 |
| 决策/下一步 | 研究者为何继续、改向或收尾 | 选项、依据、反对理由、批准者、时间和后续对象 |
| 会话/检查点 | 对话历史及模型调用所需的恢复材料 | 课题/问题关联、事件序列、压缩检查点、工具结果引用、模型信息；本身不是科学事实 |

对象关系需要支持“一项证据被多个问题引用”，而不复制多份原始文件。来源与分析的版本均可追溯。观察描述数据出现了什么，解释描述可能的原因，审核结论说明在什么范围内可以接受；它们的状态和关系由系统明确表达。系统不能因为 Agent 说“已证明”就把候选解释提升为核验事实。

### 问题树和研究分支

课题下的问题可以有父子关系、相关关系和证据复用关系。树形导航展示每个问题的简短状态，例如“待讨论、待批准、进行中、待分析、待决策、已完成、阻塞”。对于并行分支，页面应显示依赖与共同证据，而不是把所有内容压成一条聊天时间线。

问题的完成条件由研究者确认。问题完成不意味着所有实验都成功，也不意味着原始假设正确；它只说明约定的工作已完成并形成了有边界的判断，负结果、相反证据和未决解释都可以构成有效交付。

## 标准工作流

### 1. 创建课题并提供背景

研究者建立课题，填写简短方向说明，并选择工作目录、模型 API 配置和执行资源。可立即上传背景文件、论文、数据说明、配置、过往报告，也可先开始聊天后再补材料。材料显示来源和类型；“研究者认为 X”“论文声称 X”“数据观察到 X”不能在界面中混用。

系统保留文件位置、版本与内容身份。导入文件不意味着允许把全文发送到外部模型；课题设置要明确哪些内容可读取、哪些内容可用于 API，以及是否允许复制到服务器。Agent 可以从材料中提取候选摘要和主张，但它们先作为有来源的草稿，研究者确认后再进入问题或证据记录。

### 2. 创建研究问题

研究者可直接在课题下创建问题，也可在对话中要求 Agent 生成候选。研究者显式创建的问题立即形成正式对象；Agent 提出的新问题显示为待审批卡，至少包括研究边界、与现有问题关系、依据、潜在重复、预期交付物和不确定点。接受后再加入问题树；修改会更新候选版本，拒绝也可保留简要原因。

Agent 不应悄悄扩张课题范围。需要新问题或子任务时，可以先解释为什么当前问题不足以承接该工作，再给出提案供研究者决定。若用户在对话中明确要求“把这个建成问题/子任务”，该明确指令可直接作为人工创建，不再重复一轮相同确认。

### 3. 创建子任务并讨论方案

子任务表达可管理的研究工作，不等同于某条命令或某一个运行。研究者可人工创建；Agent 创建的子任务先进入审批队列，并提供目标、和父问题的关系、依赖、验收条件、预计资源及建议实验。批准子任务后，Agent 才能在该范围里持续设计和推进。

Agent 在对话中检查已有问题、事实、实验和失败记录，然后提出实验计划。任务书先是草案，可多轮修改。结构化方案应回答：准备回答什么、关键对照是什么、什么结果支持或反驳解释、输入和代码指向何处、需要多少资源、输出哪些文件、用什么规则检查完整性、怎样分析、哪些情况应停止或回报。

### 4. 审阅并冻结实验任务书

批准前，任务书展示“将执行什么”的简明摘要和可展开细节。负责人能查看输入、方法、数据访问范围、代码改动、服务器/工作目录、预算、输出位置、分析计划和失败/重试规则。批准动作冻结任务书版本及其可识别的内容引用；后续编辑生成新版本，不能静默改变已经授权的内容。

批准请求聚焦于会改变研究结果或资源边界的事项。项目可以配置不同的审批档位，例如逐次运行、在明确预算和条件下自动运行、允许有限的同条件技术重试。对代码解释、草稿分析和明确授权范围内的常规整理，不应逐个打断用户；越出目录、数据、预算、服务器、条件、问题边界或外部发送范围时，系统需要给出具体差异，重新取得授权。

### 5. 派发、执行和定时状态检查

实验由持久执行器管理，不能依赖某个聊天窗口一直保持连接。派发前预检资源、路径、输入、任务书版本和权限，生成唯一 run ID。若网络超时，先查询该 ID 对应的任务状态，不能把“没有收到回复”当作“没有启动”而盲目重复提交。

执行阶段至少区分：准备/提交中、排队、运行中、执行已结束、产物待收集、归档核验、分析中、待研究者决策、失败或状态待确认。运行进程结束、输出同步完成、文件检查通过、分析完成和研究问题解决是不同阶段，应分别显示。

状态检查采用短连接的定时查询或执行器的完成事件，不保持不必要的常驻连接。课题可选择策略：关闭自动检查、固定间隔检查、自适应间隔（运行早期较密、长时间运行逐渐放宽）或执行器事件通知。当前已有流程中需要负责人通知完成的项目，应能把这一方式配置为项目策略；其他项目可以启用自动检查和结果收集。页面显示最近检查时间、下次计划、来源及最后已知状态。

桌面关闭、断网或休眠时，远程任务是否继续由服务器执行器决定；本机任务不承诺设备休眠后仍在运行。重开应用后先恢复 run ID 并核对真实状态。轮询暂停时明确标为“状态待刷新”，不能把旧状态伪装成实时状态。连接失败与实验失败分开记录，网络恢复后继续查询，而不是自动新建一次实验。

### 6. 收集、整理并检查实验数据

任务书需声明预期产物清单，包含文件或模式、来源运行、粒度、关键字段/单位、期望数量或覆盖范围、格式解析器和保留要求。执行完成后，系统按照授权的输出路径收集文件，生成清单与哈希；检查缺件、意外文件、损坏格式、重复内容、字段不符、行数/样本覆盖与运行标识。任何无法解释的差异进入待核验区，不能靠补零、猜测字段含义或静默过滤让检查通过。

解析适配器按格式读数据，首版优先常见 CSV、JSON、日志、图像、压缩归档和简单表格；大体量或专业格式通过项目适配器扩展。数据处理工具可按文件分块、读取摘要、选择字段和抽样检查。Agent 不应把整份大型数据灌入上下文，而应读取确定性程序生成的统计摘要和相关片段，并能返回原文件及数据范围。

### 7. 分析、形成事实并对话给出下一步

收集检查完成后，系统运行任务书中约定的分析程序或分析模板。一次分析绑定输入产物版本、代码、参数、分组条件、统计单位和输出。重新分析生成新版本，原结果保留。表格和图表由分析工具计算，Agent 负责解释结果、指出异常和证据边界；不能把自然语言摘要当作数值验证。

对话中的分析答复应先回答问题，再说明关键现象、重要对照与例外、解释所依据的证据、支持或反证的范围、尚未解释之处，以及下一步可以区分哪些解释。对应的表格、图表、脚本和数据样本可展开查看。结论卡可处于“候选观察、待核验、已接受、存在争议、已更正、未决”等状态；具体状态和审核方式可由课题模板配置。

Agent 提出的下一问题、子任务或实验任务书会进入审批卡。用户可以直接继续讨论、编辑建议、拒绝，或选择“批准此任务并开始下一轮”。一键操作只批准当前显示的任务书版本和明确的资源边界；连续多轮自动执行必须是另行配置且有数量、预算和停止条件的有限授权。一次批准不构成无限循环。

## 审批和自动化边界

产品把 Agent 的推理建议、科研对象的正式变更和计算执行权限分开处理。核心规则如下：

| 行为 | 默认处理 | 需要重新审批的情况 |
| --- | --- | --- |
| 人工创建问题/子任务 | 立即建档，标记由研究者创建 | 仅当该操作还隐含外部执行或超出项目范围时 |
| Agent 提出问题/子任务 | 保存为提案，不进入正式问题树 | 每个新问题或子任务接受前由研究者确认 |
| Agent 起草任务书 | 可在对话内反复修改 | 冻结并派发运行前批准具体版本 |
| 同范围内读取、检查和分析 | 按已批准工具权限执行，记录过程 | 读取新数据、向外部服务发送内容或扩大计算边界 |
| 任务内自动多次运行 | 仅按明确限定的循环/矩阵授权 | 超出次数、预算、输入或停止条件 |
| 技术重试 | 可依策略进行有限尝试，保留旧失败记录 | 改变实验条件、算法方法、数据范围或资源预算 |
| 新的科研判断/事实 | 生成带来源和状态的候选 | 晋升为已接受结论按课题审核策略执行 |
| 删除、覆盖原始产物 | 默认禁止自动进行 | 必须有清晰预览、用户明确授权、可追踪记录和恢复策略 |

审批卡应展示具体资源与变更，不只写“Agent 想继续”。批准与运行记录都要绑定课题、问题、任务书版本、数据范围、预算、执行器和用户。模型提示词不能成为权限执行点；实际访问由操作系统沙箱、工作区范围、凭据代理及服务端策略控制。

## 大批量实验数据的组织与呈现

每轮实验可能生成大量文件、多个重复或样本级结果。产品应把“证据完整保存”和“界面易于读懂”作为同一个数据链路的两端：原始产物保留其来源，呈现层通过可追溯的摘要降低阅读成本。

### 数据层次与清理原则

每个输出必须有唯一来源身份、运行 ID、采集时间、内容哈希、解析状态、数据范围、上游产物和保留类别。数据在界面中按以下层次管理：

| 类别 | 典型内容 | 默认规则 |
| --- | --- | --- |
| 原始证据 | 预测、测量、输入快照、原始日志、运行输出、研究者上传文件 | 保持原样和来源链接；作为支撑结论的关键数据时持久保留，不自动覆盖或删除 |
| 可复现运行材料 | 代码/差异快照、配置、环境、命令、任务书、输入合同、随机性设置 | 与运行共同归档，便于复现与解释结果 |
| 分析交付 | 派生指标、表格、图表、异常清单和报告 | 记录生成程序、版本与输入；支撑已接受结论的关键交付应保留 |
| 可重算中间产物 | 缓存特征、临时转换、可由保留的源文件与程序重新生成的文件 | 标记派生关系和重算方式后，可按项目策略清理；尚未验证可重算时按重要材料保留 |
| 缓存与临时文件 | 下载缓存、临时工作目录、可重新获取的中间文件 | 仅当不再被任务或分析引用、来源已记录且策略允许时可进入清理候选 |
| 未分类内容 | 意外生成、格式未知、来源或用途不清的文件 | 隔离待分类；在研究者确认前保留，不静默丢弃 |

清理不是让模型自行决定“哪些数据没用”。系统先列出候选、来源、哈希、被哪些结论/分析引用、是否可重算及预估回收空间；用户或项目策略批准后，执行精确的文件级操作并登记日志。删除前需确认工作目录边界和备份/恢复方式。对“可重算”的判断需依赖完整源材料和成功复算验证，不能只因为文件名含 cache 或 temp。

### 在实验开始前控制产物规模

最有效的减量发生在运行前：任务书先决定需要保存哪些证据、输出到什么粒度，避免跑完以后才面对一个无法判断用途的大目录。最小保留集合由实验类型定义，用户可在批准任务书时展开修改。

| 常见计算产物 | 首版建议策略 | 必须核对的条件 |
| --- | --- | --- |
| 已有原始数据集 | 引用受管理的位置和版本，避免每轮复制一份 | 来源、访问范围和可用性；引用并不等于已有可靠备份 |
| 样本级预测与关键测量 | 保存足以复算约定指标、诊断异常和更正结论的明细 | 样本 ID、划分、单位、重复/种子与输出身份，不能仅保留一个平均数 |
| 每一步的完整张量或调试轨迹 | 按假设预先选择诊断点或样本；不要求默认全部产生 | 采样方式、未覆盖范围和触发完整诊断的条件需写入任务书 |
| 模型 checkpoint | 按任务要求保留最终版本、预定合法规则选择的版本及恢复所需版本；其余可设轮转策略 | 参数选择边界、下游复用依赖、恢复要求与重新训练代价；被结论引用的版本锁定 |
| 高频日志 | 可压缩存储，并生成阶段索引和错误摘要 | 完整原日志或约定保留范围仍可追溯；不能只留下模型生成的解释 |
| 临时特征与数据转换缓存 | 在确认来源、无引用、可重建且重算成本可接受后按策略回收 | 一个文件名或扩展名不足以判定可删除，跨分支引用也需检查 |

因此，Agent 可以建议“不生成不必要的中间文件”“压缩与去重”“只下载分析必需的列和切片”“对已确认缓存执行保留策略”。永久丢弃唯一证据、改变保留策略和删除远端持久副本应分别展示具体影响并审批。研究者可以提前授权有边界的临时文件策略，避免每次清理都被打断。

### 分析与聚合视图

研究者首先看到任务书预设的关键指标和覆盖状态，然后可下钻到分组汇总、重复/种子、样本或逐条记录。汇总必须展示聚合规则和样本范围。跨模型、数据组、协议或批次的结果只有在比较条件匹配、定义清楚时才合并；否则分组呈现。均值、分布、误差区间和异常可同时展示，不能只给一个排名或一个总体平均数。

产品可按数据结构提供以下通用视图：

| 层级 | 展示内容 | 交互 |
| --- | --- | --- |
| 运行摘要 | 运行状态、产物完整率、主要指标、预算消耗、与任务目标关系 | 对比任务书与实际运行、跳转待办 |
| 可比组 | 按任务书定义的条件分组后的指标、波动及样本数 | 选择基线和组别，显式查看不可比条件 |
| 重复/批次/子组 | 各次重复的单独结果及汇总规律 | 识别离散、异常与数据缺失，保留每次结果 |
| 样本级明细 | 与假设相关的每条观测或受控抽样 | 筛选条件、按 ID 搜索、跳到原文件/行/图像 |
| 证据路径 | 指标、图表、事实、结论与输入文件之间的来源链 | 从结论逐层打开分析版本、运行、代码、配置和原始数据 |

大文件用分页、抽样和分块读取，不要求界面一次渲染全部行；任何采样结果都注明采样规则。图表和表格可导出，导出文件保持与产物索引的版本关系。若解析器失败、关键列缺失或运行不完整，聚合应显示不完整状态并解释缺失项，不能生成看似完整的图表掩盖问题。

## 定时运行状态与后台恢复

运行状态服务与模型对话分开设计。Agent 负责确定实验计划和读取状态；持久任务管理器保存执行器 ID、检查策略、状态变更事件及最后已知位置。短时 API 请求读取一次状态后结束，不需要为每次运行保持聊天连接。

状态策略可配置固定间隔或自适应间隔，同时支持完成事件。具体间隔根据执行器能力、任务时长和成本在产品验证后设定，不在通用合同中硬编码。桌面休眠时不声称轮询仍在进行；如果服务器端调度器可继续检查，则以其实际状态为准。每次状态变更都包含“何时、从何处、根据什么凭证得知”。

网络异常或进程异常退出时，状态可标记为待确认，保留最后已知信息与诊断。启动检查失败记录为失败尝试；继续执行需先核实旧任务是否正在运行。恢复使用相同 run ID，重试使用新的 attempt ID。如此既支持 Agent 多轮工作，也避免重连时重复花费算力。

## 长对话上下文与跨窗口共享

科研记录是长期记忆，对话上下文是一次模型调用可读取的临时输入。产品不以“把整段历史永远塞进窗口”实现项目连续性。新会话根据稳定的课题与问题 ID 装载当前状态、已确认任务、有效事实、相关证据和当前任务书；需要历史细节时按引用检索对应会话与原文。

每个新会话默认带入：课题规则和权限、当前问题和子任务、已批准的未完成工作、当前任务书与运行状态、相关的已接受事实/观察/反证、关键背景材料位置、最近检查点及待决事项。近期聊天可以作为会话摘要输入；其他问题的记录先通过检索按需加载，避免不相关内容占满上下文。

会话变长时，系统在预算阈值前形成结构化检查点。压缩只改变后续模型读取的上下文视图，不删除原始消息、工具调用或结果。检查点包含当前问题、已确定决策及其来源、完成事项、未解决问题、禁止越界事项、最近运行 ID 和建议下一步；摘要中的每个事实都应指向原记录或研究对象。大型工具输出保留为可检索的证据附件，活跃上下文放摘要和相关片段。

UI 显示本轮回答实际加载了哪些研究记录、材料和会话摘要，允许用户展开来源或调整上下文。多窗口并行时以版本号检测变更：如果一个窗口刚刚批准了任务书或更新了事实，另一个窗口在使用旧版本继续运行前提醒刷新与复核。压缩、摘要或记忆检索不能改变事实状态、任务状态、研究者审批或执行权限。

此处可借鉴 Agent runtime 的会话事件、检查点、历史检索和工具输出裁剪模式，同时把规范科研对象留在独立的数据模型中。对话分支不等同于科研问题分支；聊天摘要也不等同于研究者审核过的结论。

## 技术能力分层

| 层 | 职责 | 可替换边界 |
| --- | --- | --- |
| 桌面工作台 | 对话、文件/代码检查、问题导航、审批和状态展示 | UI 形态可迭代，科研对象 ID 不依赖某个页面 |
| 通用 Agent runtime | 接入用户自选模型 API、构造上下文、工具调用、会话恢复 | 可替换模型供应商与 runtime，科研记录保持稳定 |
| 科研流程服务 | 管理课题、问题、子任务、任务书、事实、决策和审批事件 | 核心结构通用，领域字段走 schema/config 扩展 |
| 执行管理器 | 持久化运行、预算、健康检查、状态轮询和恢复 | 本地、SSH、队列系统分别提供执行器适配器 |
| 数据和产物层 | 管理文件位置、哈希、清单、模式、派生关系和检索 | 本地文件系统为首版基线，团队存储后续接入 |
| 科研工具/流程 Skills | 约束 Agent 提案和分析步骤，帮助按任务模板工作 | 可针对实验类型扩展；关键权限和状态机由程序执行 |

用户可为课题接入不同模型 API。模型供应商凭据进入系统凭据管理，不写进研究记录和运行日志。界面分别说明“允许 Agent 读取本地文件”“允许命令在指定范围运行”“允许哪些内容发送给所选模型”，不能把三者合并成一个含混的权限开关。默认方案可以是只读、工作区执行和扩大访问等少量模式，并允许查看实际生效范围。

首版集成一个运行底座和一到两个执行器即可，不同时实现多套 agent runtime。设计抽象接口的目的在于后续替换，而不是第一版就承担所有供应商和调度器。项目领域的统计规范和输出解析通过适配器、模板、脚本合同提供，通用流程不写死当前项目专用方法。

## 最小可行版本与阶段计划

### 阶段 0：交互原型验证

交付一个可点击的桌面工作区原型，验证课题切换、问题树、中央对话、代码/运行视图切换、右侧状态、问题/任务提案审批、实验任务书和运行分析卡片。使用可辨认的模拟数据演示成功、失败、状态待确认、输出不完整和下一步审批。

**退出标准：**研究者能从课题创建一路理解到运行后下一步；无需讲解即可分清问题、子任务、任务书、运行和分析；用户能在对话内批准、修改或拒绝 Agent 提案。该阶段不以模拟运行冒充真实执行能力。

### 阶段 1：课题与结构化记录

实现课题、背景材料、问题、子任务、会话关联、人工/Agent 提案审批、基础版本管理和结构化导出。先允许人工登记外部实验运行和上传结果，打通材料与问题证据的来源链。

**退出标准：**新聊天能恢复课题当前状态；Agent 生成的问题/子任务必须待审批；同一原始产物可被多个问题引用而不重复复制；导出后可追溯对象之间的关系。

### 阶段 2：实验任务书和可恢复执行

实现版本化任务书、预算/目录/资源审批、唯一 run ID、一个本地执行器和一个远程执行适配器（例如 SSH）、后台任务状态、失败尝试记录和幂等重连。执行完成通知方式按课题策略配置。

**退出标准：**批准内容与实际执行范围一致；桌面离线后可恢复查询原任务；网络超时不会盲目重复提交；同一运行的每个重试都有独立身份，失败和部分输出均能保留。

### 阶段 3：产物归档、数据分析和定时检查

实现产物清单、哈希和完整性检查，短连接定时检查/完成事件，首批常见数值格式解析器，以及配置化的可比组、重复和样本下钻。分析生成可复算的表、图、指标与报告，Agent 基于它们说明发现与不确定性。

**退出标准：**系统能够指出预期产物缺失和解析失败；分析可从保存的数据和脚本复算；视图从总体摘要下钻到原始记录；用户能看清运行完成、归档通过、分析完成和问题解决的区别；临时清理有精确预览且不触碰被引用的证据。

### 阶段 4：问题到下一轮实验的半自动闭环

实现跨会话的研究上下文装配、结构化检查点、历史检索、证据引用、下一步任务提案、单次“一键批准并运行”及有限循环授权。通过问题模板/分析适配器接入第二类计算型研究场景，验证产品通用性。

**退出标准：**长会话压缩后可从来源恢复；新会话能基于当前问题继续工作而无需复制完整历史；下一轮审批绑定确切任务书版本与预算；另一类研究只需配置或适配器，不需改核心问题/运行/证据模型。

每阶段先完成可评审工作再扩大自动化范围，不以页面数量或模型调用成功替代闭环验收。之后再考虑多用户协作、共享知识池、自动文献检索、更多模型路由、实验仪器和高阶学科包。

## 首轮产品验收场景

用一个清晰的小型计算研究场景完整演示：研究者创建课题并添加背景资料；手工创建一个研究问题；要求 Agent 提出一个子任务和实验任务书；研究者检查对照、资源和产物要求后批准；任务在本机或配置服务器运行；系统按设定时间检查状态，不保持聊天连接；运行结束后收集多文件输出，指出缺项并生成分析；Agent 在对话中解释关键发现和局限，链接回任务书、运行、分析表和原始产物；Agent 建议下一实验，研究者可以继续讨论或批准单轮执行。

至少覆盖一次运行失败后新建 attempt、一次有效负结果、一次输出不完整或字段异常，以及一次长对话后新窗口接续。每个案例的评审者都应能回答：

1. 这个实验在回答哪个问题，依据什么获批？
2. 实际运行了什么版本的代码、配置和输入？
3. 预期与实际输出是否一致，原始数据和分析在哪里？
4. 页面摘要如何聚合，能否下钻并复算？
5. 哪些内容是直接观察、哪些是解释、哪些已经审核接受？
6. 失败或异常是否被保留，重连是否避免重复运行？
7. Agent 给出的下一步为什么有价值，用户批准的范围是否明确？
8. 新会话是否能找回该问题的当前状态，而不误把旧摘要当作最新结论？

## 关键产品决策与待验证事项

1. **先确定 runtime 的嵌入方式，再承诺多模型兼容范围。**首版应验证工具调用、会话恢复、权限拦截和长任务交接，之后再决定接入多少供应商。
2. **执行器需要独立于 UI 与模型调用。**这影响桌面关闭后的运行预期和状态恢复；需要按本地、SSH 和具体调度器分别验证。
3. **“批准一次”要有可读、可撤销的边界。**用户希望自然顺畅，但审批过于宽泛会难以判断 Agent 实际获准做什么；通过任务书版本、预算、数据范围与停止条件把边界显示清楚。
4. **大批量输出先由数据工具处理，Agent 消费受控摘要。**对项目数据格式和实验单位不了解时，系统必须把它显示为待配置/待核验，而不能猜测通用统计含义。
5. **课题数据怎样存放是用户设置，而不是产品预设。**支持原位置引用或受控复制，权限、备份和清理策略按环境决定；首版要避免强行迁移用户已有工作目录。
6. **研究对象结构需要从计算型研究验证，但不能把计算领域写入通用核心。**字段合同保留类型扩展、JSON/CSV/Markdown 导出和版本演进能力。

本计划重点将现有实践中反复出现的边界显式化：当前研究状态与旧对话分开；计算结束与证据归档分开；技术失败与科学负结果分开；观察与解释分开；跨条件结果不盲目汇总；新运行与重试各自可追踪；用户批准的权限和任务书保持可检查。这些是通用产品需求，具体字段、指标和审核规则仍由每个课题定义。

## 本轮交互原型与方案的对应

2026-10-21 同步更新 [HTML 原型](prototype/research-os-prototype.html)，界面收敛到实验工作流。默认页面是中央对话，左侧是课题、问题、子任务和会话；右侧可查看进展、证据与共享事实。代码与数据是同一工作区的辅助视图。

原型可体验：新建课题、补充背景文字/文件名、人工创建问题和子任务、Agent 提案审批、任务书修改和单轮批准、独立模拟运行、模拟短连接检查及断线恢复、分析与下一轮提案、结果分组与逐种子明细、产物索引、缓存清理预览、范围结论确认、新会话和上下文检查点。界面中的所有实验数据与回复均为虚构演示。

原型尚未实现真实模型 API、文件内容解析、命令/SSH、真实定时器、统计计算和服务端持久执行。检查点展示的是交互设计；真实压缩、检索召回、并发冲突控制和权限隔离仍属于后续工程验收。技术失败、负结果、缺件、重试链与复算也保留为正式产品阶段验收项，不能以本轮正常流程的模拟代替。
