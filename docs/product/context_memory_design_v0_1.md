# 科研 Agent 的跨会话记忆与上下文管理 v0.1

日期：2026-10-21。产品设计补充，尚未实现。对应用户提出的两个实际问题：新窗口如何共享项目事实和状态；同一会话持续很久后如何避免上下文无限增长。本文定义通用机制，不绑定当前课题、模型供应商或 Agent 框架。

**核心决定：科研项目记录独立于聊天保存；每次调用模型，都按当前问题重新组装有预算的工作上下文。** 用户可以继续在原会话中工作，也可以新开窗口。聊天压缩不删除原文，不自动晋级事实，不扩大权限，不代表实验已经完成。

## 1. 哪些内容需要保存，哪些内容需要送给模型

项目越做越大时，保存全部研究历史与每轮加载全部历史是两个不同要求。系统保存完整记录，但模型每轮只接收回答当前问题所需的部分。

| 记录 | 内容与作用 | 加载规则 |
| --- | --- | --- |
| 项目规则与当前授权 | 研究范围、数据边界、预算、用户明确约束及执行范围 | 当前任务适用的规则必须加载；执行器另行检查最新授权 |
| 项目与分支状态 | 当前问题、激活任务、已完成事项、未决点、下一动作及版本 | 每轮读取当前分支的规范状态；执行前再检查版本 |
| 事实与证据 | 有适用条件、来源和核验状态的结论；支持、反证及更正关系 | 当前问题直接依赖的记录必读，其他按需检索 |
| 决策与假设 | 为什么选择某条路线、否决原因、候选解释及可证伪条件 | 当前分支及必要祖先决策加载；兄弟分支按引用加载 |
| 会话检查点 | 当前目标、讨论进度、用户纠正、未决推理及待处理工具动作 | 恢复原会话时加载；不会自动成为全项目事实 |
| 完整历史与原始材料 | 原始对话、代码版本、文件、日志、工具调用及产物 | 本地保留或登记受管理来源；通过索引按需回查 |

项目规则和状态以规范记录为准；检查点是可重建的辅助材料。论文正文、表格和日志仍是材料，不能仅因被检索进上下文就被当成用户指令。

## 2. 新窗口如何接着研究

用户新开窗口时，先选择项目和研究分支。系统读取最新项目版本、适用规则、当前任务和相关证据，生成一份短的接续说明。新窗口不必继承其他窗口的全部聊天。

例如当前任务已经派发，项目规则要求等待完成通知，那么新窗口应显示：“本分支已有运行 A16；记录中已正常启动；最后核对时间为某时；当前等待完成通知，尚未获准同步分析。”它不能从“需要验证这个问题”的旧讨论推导出再次提交实验。保存状态需要展示时间和来源，不能冒充刚查询的服务器实时状态。

两种入口需要区分：

- **新建会话**：共享项目规则、相关事实和分支状态，拥有独立的讨论工作区；其他会话的未定猜想按需引用。
- **接续某个会话**：额外加载该会话检查点、近期消息、相关原文和待处理工具记录，接着原来的讨论。

用户说“刚才第三个方案为什么没选”时，系统根据会话、方案身份和决策索引回查相应原文；没有找到就说明缺失，不凭一段通用摘要编造原因。

## 3. 一次模型调用如何组装上下文

建议增加独立的上下文管理服务，位于桌面工作台和模型适配层之间。它读取项目记录，不依赖某家模型的私人记忆格式。

组装顺序为：适用规则与当前请求 → 最新问题和任务状态 → 相关决策与直接依赖事实 → 会话检查点 → 最近完整消息与工具结果 → 按问题检索的补充证据。检索前先限定项目、研究方向、分支、版本和证据状态，再结合关键词与语义查找。

不能仅按语义相似度选择事实。若记录已被更正、存在争议或适用条件不同，组装时必须带上状态和更正关系；问题需要它的反证时，不能只返回支持材料。每轮记录使用的对象 ID、版本和材料区段，便于追查当时依据。

大日志、整份 CSV 和完整论文默认不反复注入。工具返回必要片段、可复算统计和原始位置；需要深入时再读取对应行、页或运行。截取记录必须标明已省略范围，不能把局部结果当成全部覆盖。

## 4. 同一会话变长后如何继续

用户仍在同一聊天页阅读和输入；系统维护的是模型工作上下文，历史消息继续可见、可搜索。接近工作预算时自动创建检查点，再用检查点、近期完整对话和所需记录继续。

建议流程：

1. 在一次完整回复或工具调用结束后维护上下文。先保存原始消息、工具结果及来源范围，保留尚未完成的工具调用和返回配对关系。
2. 提取本阶段新增观察、候选解释、用户决定和状态变化，按各自类型登记。来源不足的内容保留待核对，不因摘要写得确定就升级为事实。
3. 生成结构化检查点：当前目标、用户约束及纠正、已做与未做、关键决策、支持与反证、未决解释、任务和运行身份、外部动作结果、下一步，以及每项来源。
4. 检查必需字段、引用可解析性、状态版本和关键约束覆盖。用规范状态检查“已完成／未完成／未知”是否矛盾；必要时回查原文。此类检查降低遗漏风险，不能证明语义完全无损。
5. 重新组装上下文；保留最近若干完整讨论单元，不按固定消息条数生硬截断。工具和回复很长时，优先减少冗余材料。
6. 下一轮正常继续；用户能查看本次压缩保留了什么、原文在哪，并可将某条材料固定为后续任务必读。

不能长期只对上一版摘要继续摘要。每次检查点由最新规范记录、上一检查点及新增原文形成，记录覆盖范围；经过一定轮次、用户纠正关键条件或发现矛盾时，从相关原文和规范记录重建。重建也按来源范围分段完成，不要求把全部历史再次塞进同一调用。

如果固定约束、当前请求和必要证据本身已超过预算，应缩小当前子任务、分段读取，或清楚指出不可承载的部分；不能悄悄截掉条件。压缩失败时保留原状态并降级处理，不假装记忆已经可靠更新。

## 5. 预算由系统管理，并适配用户自选模型

供应商上下文上限、输出上限、工具格式和计费能力可能不同。适配层需要记录已验证的能力；无法可靠计数时采用保守估算和余量，不在配置未知时声称还能容纳确定数量的消息。

可用输入预算需要扣除系统规则、工具定义、预留输出、预计工具返回及余量。产品另外设置日常工作预算，避免每轮都加载模型允许的最大材料。阈值根据实际调用成本、延迟和接续测试调整。

原型初值可用“工作预算约六成开始维护、约八成要求重建”测试；这是产品待验证参数，并非模型通用最佳实践。必须按下一次请求的完整组装体积判断，不能只数聊天文本。切换到更小上下文模型时先重新组装；不能静默裁剪已有任务。

## 6. 多个分支和窗口如何共享而不相互覆盖

同一项目的窗口读取同一个本地科研服务与版本化记录，各自保留会话工作区。每个分支维护自己的当前任务和下一动作；项目协调视图汇总依赖，不把所有分支硬塞进一个串行会话。

共享分三层：研究方向下已核验的范围事实可引用；本分支观察和假设默认留在本分支；个人会话草稿和临时推理仅在明确引用时传递。来源身份保持唯一，引用不会复制出一次新实验。

在每轮开始和关键写入前检查版本。若窗口 A 已更正事实，而窗口 B 正在基于旧版本生成方案，B 的写入需检测冲突并重新核对依据。数据库事务和版本条件负责避免覆盖，模型自己“记得比较版本”不能作为唯一保证。事实晋级、任务激活和预算占用通过对应对象的受控提交串行完成；独立阅读和分析可以并行。

生成过程中相关事实被撤回、授权改变或分支状态更新时，本地服务应标记该次调用的依据已变化。正在显示的回复提示需要重新核对，不能继续把旧建议呈现为当前有效决定；下一工具动作先检查最新状态。已发出的计算另按执行器实际状态处理，不能仅因上下文失效就声称已取消。

外部执行还需要运行台账。任务和尝试 ID、执行位置、请求标识及提交结果先持久化；执行器支持幂等请求时复用同一标识。断线或崩溃导致提交结果未知时，先按项目策略核对既有任务，不能直接再跑一次。检查点不代替运行台账，也不代替当前授权。

## 7. 把当前项目经验变成通用产品规则

| 当前项目中的做法或痛点 | 通用产品机制 |
| --- | --- |
| 用 CURRENT_STATE 和问题文档恢复焦点 | 版本化的项目、分支和任务状态；新窗口自动接续 |
| facts 将已核验、观察、未决和更正分开 | 类型化记忆；压缩和检索不能改变证据等级 |
| 完成计算与本地归档不是同一状态 | 运行、产物、分析和审核独立保存，按记录恢复 |
| 启动后停止监听，等待通知 | 项目级执行策略进入适用规则，摘要不能扩大授权 |
| 历史很多，全部加载会淹没当前问题 | 当前状态与直接依赖优先，历史按对象和引用读取 |
| 新会话容易重复做已完成工作 | 完成台账、运行身份和版本检查先于行动建议 |

此处是从仓库结构和当前合同抽取的设计要求，不声称现有文件体系已经实现自动上下文管理，也不把当前课题的等待通知策略强制用于所有项目。

## 8. 工作台需要增加的交互

输入框附近显示“上下文：自动管理”，点击打开右侧“当前上下文”抽屉，展示本轮模型、估算工作预算、项目状态版本、已加载事实与证据、会话检查点、尚未加载的材料和最近维护时间。条目可追溯到来源。

聊天时间线显示轻量标记：“已整理本阶段，原始记录可回看”。用户可查看检查点、固定关键约束、纠正记录、从该阶段新开会话。纠正生成新版本并保留旧来源，不直接改写已接受事实。

新窗口显示简短接续卡：当前问题、沿用的事实范围、已运行任务、未决点和下一动作；关键状态标注最后核对时间。用户无需手工复制一长段启动提示。

默认自动管理，预算、固定材料和共享范围在高级设置展开。不能只有一个 token 百分比，让用户自行判断系统到底忘了什么。

## 9. MVP 交付和验收

第一版应实现本地规范记录与来源索引、项目及分支状态版本、会话检查点、按问题组装上下文、原文回查、预算管理、运行台账和冲突检查。全文索引可先满足明确对象与关键词查询；向量检索和复杂记忆图谱后续增加。

验收用固定的研究接续样例，包括：长日志、用户后期纠正、适用条件不同的事实、失败实验、事实撤回、两个窗口同时更新、生成过程中依据变化、压缩中途崩溃和切换小模型。检查连续多次压缩及恢复后，是否还能正确回答“做了什么、依据是什么、还缺什么、允许做什么、唯一下一动作是什么”。

关键约束缺失、未核验观察被晋级、撤回事实被当成现行依据、已有实验被重复派发，应作为阻断问题。另评估来源命中、关键信息遗漏、任务表现、延迟和调用成本。原文可追溯只能使错误可调查，不能承诺模型压缩绝不丢信息。

## 10. 工程实现优先复用开源能力

先核对成熟项目的实际代码、测试、许可和扩展接口，再决定直接接入、通过适配层使用或仅借鉴机制。底层选择以同一组科研接续样例验证；不因为多个项目各有优点，就把多套运行框架全部叠加进首版。

模型调用、工具调用、会话存储、上下文裁剪和检查点优先复用通用运行层。科研问题、事实等级、证据范围、更正链、实验身份和研究状态由独立业务服务管理。运行框架的会话树不等于科研问题树，自动摘要也不等于已核验事实池。

LangGraph 已提供线程内检查点与跨线程 Store 两类持久化接口，可借鉴这种分工。官方文档明确区分线程状态恢复和跨线程应用记录，源码也分别定义 BaseCheckpointSaver 与 BaseStore。是否采用其运行框架仍待嵌入验证；即使采用，科研对象、共享范围及冲突语义仍需自行定义。[持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence) · [检查点接口](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py) · [跨会话存储接口](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/store/base/__init__.py)。

本次通过官方 raw 源码核对 LangGraph 根 LICENSE 为 MIT；未固定该仓库提交 SHA，接入前需固定版本并重新检查直接和传递依赖。文档示例里的内存存储仅适合验证概念，进程重启后的恢复需使用持久存储。
