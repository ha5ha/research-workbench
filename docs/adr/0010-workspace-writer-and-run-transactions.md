# ADR-0010：工作区单写者与运行审计事务

- 状态：Accepted（2026-11-11，所有者要求完成并真实验证 1.0，授权必要的数据可靠性加固）
- 关联：ADR-0006/0007/0009、项目路线 G0/G1/G5

## 问题与约束

桌面单实例锁不能阻止独立 Core CLI 同时打开同一工作区。研究树的进程内写队列和 RunStore 的活动运行检查不能提供跨进程单写者保证。当前产品不支持多人/多 Core 并发写入，因此应在 Core 启动时明确拒绝第二写者，而不是引入合并协议。

RunStore.update 先更新运行，再单独插入状态事件；事件写入失败或中途崩溃会留下缺失审计依据的状态。两次数据库写入必须在同一 SQLite 事务中提交或回滚。文件/远端 Job 的核对机制继续保持，不把数据库事务误当跨系统事务。

## 候选、复用与许可

复用现有 `node:sqlite` / SQLite；不新增、升级或分发第三方锁库。Node 最低版本保持 22.19.0，实际运行版本与构建证据记录在发布验收中；SQLite 版本来自该 Node/Electron runtime，不独立下载。已有 Node/SQLite 的许可与打包责任继续纳入分发清单。这里比较现有实现的三种使用边界，不再引入第二套锁实现。

| 候选 | 适配与恢复成本 | 结论 |
|---|---|---|
| 独立 SQLite 锁库连接持有 `BEGIN EXCLUSIVE` | 复用 OS/SQLite 文件锁；进程退出自动释放；不占用科研主库事务；一个小型持久锁文件，无新依赖 | 采用 |
| 主 workbench.db 全生命周期持有 EXCLUSIVE 事务 | 同样复用 SQLite，但会与 RunStore 的运行意图和更新事务冲突，改变业务连接语义 | 不采用 |
| `mkdir` / PID 文件自研租约 | 需要处理崩溃后的陈旧锁、PID 复用和抢占竞态；退出清理本身不能保证安全 | 不采用 |

SQLite 是仓库已有且满足跨进程/崩溃释放边界的成熟实现，故本次没有新增外部候选依赖。主库状态/事件事务也直接使用现有 `BEGIN IMMEDIATE`，与 createRun 的机制一致。

## 决策与边界

1. ExperimentStore 是生产 Core 的数据库所有者。在打开科研主库与启动研究服务/RPC 前，先持有 `.research/workbench.lock.db` 的独占事务；第二实例明确报告工作区正在使用。
2. 主库与锁库及其 sidecar 均拒绝链接、硬链接或非普通文件。初始化任一步失败立即关闭已打开连接；正常关闭先关主库再释放锁，关闭幂等。
3. 锁文件保留，不依据 PID 或时间删除/抢占。崩溃后由 OS 释放锁，下一实例直接取得锁；不要通过删除锁文件“解锁”。
4. 支持本地文件系统上的单 Core 工作区，不承诺网络共享盘、多 Core 写入或外部程序绕过服务直接修改科研数据。独立 ResearchService helper 仍只提供进程内排队。
5. RunStore.update 的运行状态与事件一起提交；任一失败都回滚。已有终态不可静默覆盖、取消请求保留与 unknown 核对规则不变。

## Windows 终止失败路径

受管回归在受限工具沙箱中稳定暴露 `taskkill /T` 被拒后的旧 fallback：只杀 PowerShell 根进程，Node 孙进程继续持有输出管道，supervisor 永久等待且失去可重试的进程树根。相同回归在沙箱外通过，证明权限拒绝是触发条件；不能以成功重试掩盖这个失败路径。

保留系统 taskkill 为 Windows 树终止实现，不引入原生 Job Object 依赖。树终止失败时保留根进程和停止原因、记录失败并重试；Core 继续显示 unknown，不把仍可能运行的研究进程记为已终止。拒绝只杀根的 fallback；完整原生 Job Object 可单独评估，不是本次新增依赖的理由。用可控 taskkill 不可执行 fixture 验证失败后恢复与整树终止。

## 验证与退出

测试同进程/真双进程竞争、不同工作区互不阻塞、显式关闭后重开、持锁进程被强制终止后无人工清理恢复，以及主库初始化失败后锁释放。链接 fixture 只在临时目录，外部 sentinel 必须不变。

用 SQLite trigger 注入事件写入失败，核对状态和事件同时回滚，随后正常更新可以提交。继续执行受管运行/恢复与记录完整性回归。

回滚时先关闭 Core 并核对活动 Job，保留科研主库、plans/jobs 和证据；锁库本身不含科研对象，不删除仍可能被进程持有的锁文件。后续迁移数据层时保留相同单写者契约，只有引入经过验证的多写者事务/版本策略后才能替换此边界。
