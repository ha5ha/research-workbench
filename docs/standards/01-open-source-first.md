# 01 · 开源优先规范（Open Source First）

## 1. 目的

用成熟开源降低通用能力成本，把自研精力留给真正差异化的部分：**科研对象、实验闭环、证据链和原型级桌面交互**。

“开源优先”不等于“能装就装”。必须评估许可证、维护状态、边界匹配度和替换成本。

## 2. 强制流程

任何新能力、组件或基础设施，在写第一行业务代码前：

### 2.1 检索

- 优先检索官方仓库、官方文档、release/tag 和源码，而不是只看博客/二手文章。
- 至少比较 2 个候选；只有一个候选时，说明原因。
- 检查：最近发布、issue/PR 活跃度、维护者、测试、文档、安全公告。
- 检查直接与传递依赖的许可证。

### 2.2 判定

按以下优先级决策：

```text
直接采用（Adopt）
  → 通过适配层使用（Adapt）
    → 参考机制自行实现（Reference）
      → 自研（Build）
```

选择“自研”必须满足至少一条：

- 没有许可证兼容、边界匹配的实现；
- 现有实现会引入不可接受的运行时/视觉/安全耦合；
- 该能力是本产品的核心差异化，且自研成本可控；
- 需要修改的深度已经超过维护 fork 的成本。

### 2.3 记录

在 `docs/adr/` 新增 ADR，至少包含：

- 问题与约束；
- 候选项目与许可证；
- 维护状态与版本；
- 选择/拒绝理由；
- 固定版本或 commit；
- 验证方式；
- 退出/替换策略。

### 2.4 固定

- `package.json` 不使用 `latest`、`*` 漂移版本。
- 外部二进制/服务记录版本或 commit。
- 升级必须跑集成测试，并更新 ADR/NOTICE；跨大版本必须单独评审。

## 3. 许可证规则

| 许可证 | 处理 |
| --- | --- |
| MIT / BSD / Apache-2.0 / ISC | 可优先评估；保留版权与 NOTICE |
| MPL-2.0 | 可评估；修改文件需按 MPL 开源 |
| LGPL | 只允许动态链接/独立进程边界，需评审 |
| GPL / AGPL | 禁止直接链接进客户端；如必须，只能独立服务边界并取得明确书面批准 |
| 无许可证 / 自定义限制 | 视为不可用 |

任何许可证结论都必须以仓库根 LICENSE 与依赖清单为准，不凭 README 一句话。

## 4. 依赖边界

- 第三方 SDK **必须**封装在适配层；业务代码不得到处直接 import。
- 同一能力只允许一个主实现：一个 Agent runtime、一个数据库驱动、一个设计系统、一个日期库（除非有明确例外）。
- 引入 UI 组件库时，只能使用无样式/可完全接管样式的原语；禁止默认主题覆盖原型视觉。
- 引入运行时框架前，必须完成嵌入 spike、打包 spike 和权限拦截 spike。

## 5. 历史方案主选与实际采用

下表为方案选型，不表示每项已经引入。当前生产代码使用 node:sqlite；Drizzle、Radix、node-pty、xterm.js、Shiki 尚未按方案完整交付。实际直接依赖、固定版本和许可声明见[依赖台账](../project/dependencies.md)。新增/升级仍需 ADR。

| 能力 | 主选 | 许可 | 状态 |
| --- | --- | --- | --- |
| Agent runtime | pi SDK | MIT | Phase 0 验证后锁定 |
| 桌面壳 | Electron | MIT | 采用 |
| UI 框架 | React + Vite | MIT | 采用 |
| 数据 | SQLite + Drizzle | MIT / Apache-2.0 | 采用 |
| UI 行为原语 | Radix Primitives | MIT | 采用 |
| 终端 | node-pty + xterm.js | MIT | 采用 |
| 代码查看 | CodeMirror 6 + Shiki | MIT | 采用 |

参考但不作为依赖：DeepSeek Harness（MIT）、Codex（Apache-2.0）、OpenCode、LangGraph（MIT）。

## 6. 禁止事项

- 为了“生态大而全”同时接两套 Agent runtime。
- 引入会覆盖原型的 UI 主题。
- 把参考项目整仓复制进来而不记录来源/许可证。
- 在未验证 Windows 打包前，把关键依赖押在原生模块上。
- 把“开源”当成免审理由；安全、维护和许可证仍必须检查。
